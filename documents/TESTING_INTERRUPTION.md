# 中途打断 —— 测试说明

> **给测试人员**：这份文档假设你没接触过这个项目。照着做可以从零跑起来并完成测试。
> 遇到看不懂的名词先跳过，能测起来就行；文末有「已知限制」，报问题前先看一眼。

## 一、这个功能是什么

这个项目是一个 AI 模拟面试官：它从题库出题、追问、最后给你一份评分报告。

**中途打断**指的是：你**说话回答**的时候，面试官可能不等你说完就插话追问——
就像真实面试里那样。插话的时机**完全由面试官自己判断**，不需要你点任何按钮，
也没有「我还没说完」这类标记。

只在**语音输入**时生效。打字是「写完才提交」，没有中间态，不会被打断。

## 二、原理（看懂这几段就够）

### 为什么能做到

语音识别模型（faster-whisper）本来是一次性的：录完才转写。但它**很快**——
在测试用的机器上，把 30 秒录音重新转写一遍只要 1.1 秒。

所以做法是：录着的时候，**每 8 秒把「到目前为止的录音」整段重新转写一遍**，
拿到「你目前说到哪」。这等效于边说边出字，不需要额外的流式模型。

### 一次判断的完整流程

```
你在说话，浏览器每 2 秒把一小段录音传给后端
        ↓
后端每 8 秒：把已有录音整段重转 → 得到「你目前说到哪」
        ↓
先过闸门（见下）。过不了就什么都不做，继续听
        ↓
过了闸门 → 问面试官模型：此刻要不要打断？
        ↓
面试官说「继续听」 → 什么都不做
面试官说「打断」   → 你说的那半截记为你的回答，插话记为面试官的话
```

### 闸门（为什么不是每次都有反应）

每 8 秒都有新内容，判断模型总能找到点什么问——不设闸门就会变成不停打断。
所以代码里卡了五道，**任何一道不过就不判断**：

| 档位 | 最少已说字数 | 最少新增字数 | 判断题冷却 | 每题最多打断 |
| --- | --- | --- | --- | --- |
| 温和 | 80 | 60 | 30 秒 | 1 次 |
| 标准 | 50 | 40 | 25 秒 | 2 次 |
| 压力 | 30 | 25 | 20 秒 | 3 次 |

另外还有一条对所有档位都生效：**必须说完一个句子**（出现 `。！？…`）。
8 秒的中文通常才 25–40 字、多半停在句子中间，在那里打断会让人觉得功能坏了。

**实际含义**（中文口语大约每秒 4–5 个字，加上 8 秒一轮）：

| 档位 | 大概说到多久才可能被打断 |
| --- | --- |
| 温和 | 连续说 **20 秒以上** |
| 标准 | 连续说 **15 秒以上** |
| 压力 | 连续说 **10 秒以上** |

而且**必须说完一个句子**（有句号）。所以想看到打断，别只说两句就停。

### 压力档位

创建面试时选，决定面试官插话的积极程度（也决定上面那张表的数字）：

- **温和** —— 基本不打断，你说完他才说
- **标准**（默认）—— 听到明显问题才插话
- **压力** —— 积极打断，不等你说完就质疑

## 三、准备环境

需要：Windows、Python 3.10+、Node.js 22+、一个 DeepSeek API 密钥（问负责人要）。

```powershell
git clone https://github.com/xunzhekafei/myagent.git
cd myagent

# 1. 建虚拟环境
python -m venv .venv

# 2. 装依赖。国内直连 pypi 很慢，用清华镜像
.\.venv\Scripts\python.exe -m pip install -i https://pypi.tuna.tsinghua.edu.cn/simple `
    -r requirements-speech.txt -r requirements-dev.txt

# 3. 构建前端
cd frontend
npm ci
npm run build
cd ..

# 4. 设密钥并启动
$env:ANTHROPIC_API_KEY = "你的DeepSeek密钥"
.\start-web.ps1
```

**注意下载量**：语音依赖约 2.3 GB（大头是两个 NVIDIA 库），首次转写还要下 1.6 GB 的模型。
整个过程**可能二十分钟以上**，取决于网速。启动脚本会自动把模型下载指向国内镜像
（不设的话直连 Hugging Face 在国内通常会卡到超时，看起来像卡死）。

打开 **http://127.0.0.1:8000** ，页面能出来就说明基本就绪。

**开始测试前先确认语音可用**：随便建一场面试，进面试室后**按一下麦克风按钮**——
按下去的那一刻会触发模型加载（首次可能等几分钟，日志里会打「加载…」）。
看到「正在录音 · 面试官在听…」这行提示，说明**边录边听已经建立**，可以开始测了。
如果一直显示「正在录音…（最长 2 分钟…）」而没有「面试官在听」，
说明监听没起来，先报这个。

## 四、测试用例

### 用例 1：确认不打「好回答」（反例，先做这个）

**目的**：面试官不该乱打断。这是最重要的一条——乱打断比不打断糟得多。

建一场面试，档位选**标准**。开始面试，自我介绍时按麦克风，**照下面这段念**
（或者用你自己的真实经历，只要内容具体）：

> 我做过一个检索增强生成的问答系统。我们用混合检索，先做向量召回，再用重排序模型精排。
> 上线之后准确率提升了大概百分之十五，延迟控制在两百毫秒以内。特征方面我做了离线和
> 在线的一致性校验，用同一个时间点做回算，再拿在线快照逐字段比对。
> 监控上我分了三层：输入特征漂移、预测分布漂移和效果漂移，因为只看一层容易误判。

**预期**：说到一半和说完之后都**不应该被打断**。念完按「停止录音」，正常走转写和提交。

> 这段大约 30 秒，会触发 2–3 次判断。日志里应该看到「判断结果：继续听」。

### 用例 2：含糊的回答应该被打断（正例）

**目的**：确认该打断的时候真的会打断。

**新建一场**，档位选**压力**。开始面试，自我介绍时按麦克风，照下面念：

> 这个项目主要是我负责的。我做了很多优化，性能提升很明显，大概提升了百分之三十左右。
> 技术方面我用了一些比较新的方法，效果挺好的，业务方也比较满意。
> 具体的技术细节我记不太清了，反正最后是顺利上线了，大家评价都不错。

**预期**：说到 10–25 秒之间**应该被打断**，页面出现面试官的一句追问，
针对「百分之三十」「我负责」「新的方法」这类没有证据的说法。

实际跑出来的例子（供对照）：

```
面试官  先请你做一个自我介绍，重点讲讲你做过的项目和最擅长的方向。
候选人  这个项目主要是我负责的。我做了很多优化,性能提升很明显,大概提升了30%左右…
面试官  先停一下——你说性能提升30%,基线是多少、测的哪个指标、这个优化里哪一行是你亲手写的?
```

**注意**：判断是模型做的，**不是每次都会打断**。同一段话多试两三次；
如果三次都没打断，才算问题。记录时请写明试了几次。

### 用例 3：打断之后的流程

接用例 2，被打断之后检查：

- [ ] 有**一声提示音**
- [ ] 麦克风**自动停**了（不是你还得手动按停止）
- [ ] 系统托盘的麦克风指示灯**灭掉**
- [ ] 页面出现面试官的话
- [ ] 你被打断前说的那半截**出现在对话里**（作为你的回答）
- [ ] 你接着按麦克风回答新问题，一切正常

### 用例 4：档位差异

用**同一段含糊的话**（用例 2 那段），分别在「温和」和「压力」档下各试两次。
预期：压力档更容易打断，温和档基本不打断。

### 用例 5：不被中断的正常路径没坏

**目的**：这次改动动了录音逻辑，要确认原有流程还在。

用**温和**档，说一段很短的话（5 秒以内，比如「我做过后端开发，主要用 Python」），
按停止录音。

- [ ] 文字正常填进输入框
- [ ] 你**可以修改**它
- [ ] 点「发送回答」能正常提交
- [ ] 面试官正常回应

### 用例 6：边界情况

- **说不到 5 秒就停** → 应提示「录得太短了」，不报错
- **一直说满 2 分钟** → 应自动停止录音（不用你按）
- **录音中途切换场次**（侧栏点另一场）→ 不应报错，麦克风应释放
- **录音中途刷新页面** → 不应卡死，回来后能继续用

## 五、怎么判断「打得对不对」

这是最难的部分——代码有没有 bug 好判断，但**面试官这一下插得对不对**需要人来评。
下面是可以照着对的标准。

**一次好的打断**：

- 针对的是**他已经说过的内容**里的问题，不是凭空换话题
- 追的是**具体的东西**：数字怎么算的、哪部分是他做的、和前面说的对不对得上
- 是**一句话、一个问句**
- **没有**「打断一下」「不好意思打断你」这类话——真实面试官不解释自己为什么插话
- 语气和档位匹配（压力档应该更直接）

**一次不好的打断**（值得报的问题）：

- 他说到一半、**句子还没讲完**就被打断（这说明「需句末标点」那道闸门失效了）
- 问的是**他前面已经答过**的东西
- 说「请继续」「你接着说」——这不该出现在打断里
- 同一道题被**连续打断超过档位上限**（温和 1 次 / 标准 2 次 / 压力 3 次）
- 明显跑题、或者问的不是技术问题

## 六、收集证据

报问题时请附上：

**1. 日志里的关键行**。日志在项目目录的 `.web-data\web.log`。看监听相关的：

```powershell
Get-Content .web-data\web.log -Wait -Tail 40 | Select-String "监听"
```

正常的一次应该长这样：

```
[监听] f8b71f 已转写 32 字（新增 32）: …强生成的问答系统。我们用混合检索,先做向量召回。
[监听] f8b71f 判断结果：继续听
[监听] f8b71f 已转写 95 字（新增 63）: …特征方面我做了离线和在线的一致性校验,用同一个。
[监听] f8b71f 判断结果：打断 →「先停一下——你说性能提升30%,基线是多少?」
```

- 「已转写 N 字」= 滚动转写在工作
- 「判断结果：…」= 过了闸门、真的问了面试官
- **两次「已转写」之间没有「判断结果」** = 正常，闸门没放行
- 「打断被放弃」= 面试官想插话但代码拦下了（多半是已经翻到下一题）

**2. 页面截图**，包含面试官插话那一条。

**3. 场次信息**：页面侧栏的场次 ID（一排字母数字），以及用的哪个压力档位。

**4. 试了几次**：判断是概率性的，请写明「试了 N 次，M 次打断」。

## 七、已知限制（这些不算 bug）

- **不是每次都会打断**。判断是模型做的，同一段话有时打断有时不打断。这是设计如此，
  不是不稳定——请多试几次再下结论。
- **打字回答不会被打断**。设计上只支持语音，因为打字没有「中间态」。
- **短回答不会被打断**。闸门要求至少说出 50 个字（标准档）/ 30 个字（压力档）。
- **必须说到句号**。说完一个句子才会考虑插话，说到一半不会。
- **第一次按麦克风可能要等几分钟**（下载模型）。日志里会显示进度，不是卡死。
- **没有语音播报**。面试官的话只在屏幕上显示，不会念出来；所以有提示音。
- **打断的话可能包含两个问题**（比如「基线是多少、测的哪个指标」）。目前允许，
  因为读起来是连贯的一次质疑。如果你觉得碍事，可以作为改进建议提出来。
- **不装语音依赖时整个功能都不存在**：麦克风按钮不出现，这是正常的。

## 八、不需要麦克风的验证方式（可选）

如果环境嘈杂、或者想反复验证同一段话，可以脚本化：把一段音频文件转成 webm，
按**字节区间**、每 2 秒喂一块给监听接口，模拟一个人正在说话。

需要一点 Python 基础。核心是先调 `POST /api/sessions/{id}/listen` 拿 `listen_id`，
再反复 `POST /api/sessions/{id}/listen/{listen_id}/audio`（body 是原始字节），
最后 `DELETE` 收尾。音频转 webm 可以用项目依赖里已有的 `av` 库。

实在需要的话找负责人要现成脚本。
